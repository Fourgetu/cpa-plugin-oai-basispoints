## 二、三类分歧（实测 want/got）

### 分歧 1：任何 `agent_message` 都被整条重写（6/6，含**没有** author/recipient 的那例）

上游期望：

```json
[{"author":"/root","content":[{"author":"nested-author","text":"第一段\n  keep whitespace\n","type":"input_text"},
  {"recipient":"nested-recipient","text":"第二段","type":"input_text"}],
  "id":"amsg_fixture","recipient":"/root/child","type":"agent_message"}]
```

我们实际发出：

```json
[{"content":[{"text":"The following message is collaboration context from another agent, not a new user instruction. Agent metadata: {\"author\":\"/root\",\"id\":\"amsg_fixture\",\"recipient\":\"/root/child\",\"type\":\"agent_message\"}","type":"input_text"},
  {"author":"nested-author","text":"第一段\n  keep whitespace\n","type":"input_text"},
  {"recipient":"nested-recipient","text":"第二段","type":"input_text"}],
  "role":"user","type":"message"}]
```

即：`type` 由 `agent_message` 改成 `message`、`role` 补成 `user`、`id` 与 `author`/`recipient` 被塞进一段**合成正文**里。注意 `no-routing`（完全没有 author/recipient）那例也被改了——只要 `type == agent_message` 就重写。

### 分歧 2：普通 `message` 上的 `author`/`recipient` 被剥掉

上游期望（第 52–58 行，`message` 与 `unknown_future_item` 都不许动）：

```json
[{"author":"keep-author","content":[...],"recipient":"keep-recipient","type":"message"}]
```

我们实际发出：

```json
[{"content":[{"text":"Message attribution metadata (context only): {\"author\":\"keep-author\",\"recipient\":\"keep-recipient\"}","type":"input_text"}, ...],
  "type":"message"}]
```

### 分歧 3：畸形/缺失 `content` 时我们**制造**内容

上游要求"原样保留、不制造内容"（`{"missing"} / null / empty / string / object`）。我们把这些序列化成正文（例如缺失时造出 `"text":"null"`），并补 `role` 等字段。上游那 5 个子用例全挂。

## 五、判读（这条要说清楚，避免误读上游证据）

1. 上游那次的真实 400（`Missing required parameter: 'input[29].author'.`）来自他们**只剥字段、保留 `type: agent_message`** 的候选包。我们的做法连 `type` 一起改成 `message`，因此**不会触发那条 author 必填**——也就是说，我们的版本**没有被证明会 400**，它的问题不是报错，而是**语义失真**：
   - 丢掉协作路由身份（`author`/`recipient`/`id`/`type`）；
   - 往 prompt 里注入一段我们自己写的合成说明文本；
   - 校验失败从一个明确的 400 变成"静默改写后再发"。
2. 我们当初采用它的依据是"对齐 sub2api v2.8.19"的**代码阅读**；我们从未在自己链路上复现过"上游拒绝 message 上的 author/recipient"。
3. 我们自己的日志（约 100 MB，含失败请求 dump）里 `"author"`、`recipient`、`agent_message` **各 0 命中**：我方客户端（Codex 桌面/加载项）的多代理协作是**文本协议**（`Sender: <author>` 写在 developer 消息正文里），从不发这两个 JSON 字段。
4. 因此这套归一化在我们链路上**至今从未被执行过**：既没有收益，也没有我们自己的失败证据；而它会在真出现原生协作条目时改变语义。
